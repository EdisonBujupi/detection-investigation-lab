\# Ubuntu Auditd Telemetry



\## Purpose



Document the Linux audit telemetry used by the monitored Ubuntu endpoint.



The purpose of this capability is to establish reliable endpoint process-execution visibility before building detections on top of it.



\## Target Capability



The first telemetry capability must allow an investigation to answer:



\* Which process executed?

\* When did it execute?

\* Under which identity did it execute?

\* Which executable generated the event?

\* Can the event be correlated with other endpoint or network evidence?



\## Current State



The monitored endpoint is:



\* Host: `wazuh-agent`

\* IP: `192.168.51.135`

\* Operating system: Ubuntu

\* Telemetry component: `auditd`



Initial validation established:



\* `auditd` is installed and running.

\* Kernel auditing is enabled.

\* `auditctl` is available.

\* Audit event loss is currently `0`.

\* The audit backlog is currently `0`.

\* No event-specific audit rules are currently configured.



The existing `/etc/audit/rules.d/audit.rules` contains only baseline audit configuration:



```text

\-D

\-b 8192

\--backlog\_wait\_time 60000

\-f 1

```



Therefore, the audit subsystem is operational, but it is not currently configured to generate the specific process-execution events required by this investigation workflow.



> This does not mean the endpoint has no telemetry. Other Wazuh-collected logs may still exist. It means `auditd` itself is not currently configured for the required event-specific process telemetry.



\## Implementation Strategy



Process-execution visibility will be introduced as a narrowly scoped audit capability.



The implementation should:



1\. Add only the required process-execution rule.

2\. Load and validate the rule.

3\. Generate a controlled process-execution event.

4\. Inspect the raw audit evidence.

5\. Confirm that the event contains the fields required for investigation.

6\. Confirm that Wazuh can ingest the resulting telemetry.

7\. Only then build a detection around the telemetry.



Broad audit collection should be avoided unless a later investigation requirement demonstrates that additional telemetry is necessary.



\## Validation Strategy



The expected validation chain is:



```text

Audit Rule

&#x20;   ↓

Controlled Process Execution

&#x20;   ↓

Raw Audit Event

&#x20;   ↓

Identity + Executable + Timestamp + Process Metadata

&#x20;   ↓

Wazuh Ingestion

&#x20;   ↓

Detection

&#x20;   ↓

Investigation

```



Each stage must be validated independently.



A successful configuration change is not considered sufficient evidence that the telemetry pipeline works.



\## Evidence Requirements



A useful process-execution event should provide enough information to establish at least:



\* event timestamp

\* executing identity / audit identity

\* executable

\* process ID where available

\* audit event identifier

\* audit rule key



Additional fields will be documented after observing the actual event generated by the endpoint.



\## Security and Privacy



Raw endpoint telemetry may contain:



\* usernames

\* hostnames

\* file paths

\* command arguments

\* process information

\* network information



Raw production-style telemetry should therefore not be committed to the public repository.



The repository should contain sanitized evidence, representative examples, detection logic, investigation notes, and reproducible configuration rather than sensitive endpoint data.



\## Current Decision



No event-specific audit rule has been added yet.



The next implementation step is to introduce the process-execution rule, validate the resulting raw audit event locally, and determine whether the resulting telemetry is sufficient for the investigation workflow.
